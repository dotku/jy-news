随后，微软回应了这些担忧，承诺将继续把 WinUI 作为 Windows 11 的原生框架，而不是另起炉灶开发新的解决方案和设计语言。微软还表示，计划公开 WinUI 的开发过程，以提高透明度并加快开发速度。如今，这一转变正在真正发生。

微软在 GitHub 上确认，WinUI 的主线开发已经完全公开进行。无论是普通用户还是开发者，都可以实时关注项目进展。

微软在 GitHub 帖子中确认：“WinUI 的主线开发现在正在 GitHub 上进行。WinUI 工程师以及微软的其他开发者正在这个代码库中创建分支、发起拉取请求、审查代码、进行验证并合并更改。”

微软还表示：“我们日常的工程工作现在都在公开环境中进行，因此大家可以实时关注进展，而不必等到更改正式发布后才看到结果。”

这一举措在一定程度上让人相信，经历多年网页应用发展后，WinUI 仍然受到微软重视，微软在 Build 大会上作出的承诺并非只是宣传或公关话术。

微软内部人士表示这项工作是微软重新带回 Windows“原生”体验这一更大目标的一部分，也与 Windows 工程负责人鲁迪·胡因此前提到的“100% 原生”应用方向一致。

这并不意味着微软会放弃其他开发框架。不过从今以后，原生应用将成为重点，至少对于系统内置或预装应用来说是这样。

对于不熟悉 WinUI 的用户来说，WinUI 是一套遵循 Windows 11 设计规范的开发框架，支持圆角界面、Acrylic 和 Mica 等 Fluent Design 设计元素、更流畅的动画以及深色模式。

目前，WinUI 已经应用于 Windows 设置、Microsoft Store、通知中心以及文件资源管理器的部分区域，但在整个操作系统中的覆盖范围仍然有限。微软希望逐步解决这一问题，最终将所有界面迁移到 WinUI，包括文件资源管理器中“属性”窗口等传统对话框。

微软认为，Windows 当前真正需要解决的并不是传统应用或 Win32 应用。即便这些应用的外观与 Windows 11 不完全一致，也不一定会导致电脑运行速度变慢。更大的问题在于基于 WebView2 的应用，尤其是 Electron 应用，它们可能占用数GB内存。

Discord 就是典型例子之一。其开发者曾警告称，Windows 版 Discord 的内存占用可能超过 4GB。当这种情况发生时，Discord 会重启应用的部分组件，同时尽量确保用户的工作不会被打断。

Windows 天气应用的内存占用也超过 1GB，而微软 Teams 的性能问题同样广为人知，以至于微软正在为低端电脑开发一种“效率模式”。

WinUI 重新获得重视后，最大的潜在好处是，Windows 长期以来形成的网页应用问题最终有望得到缓解。近年来，不仅第三方开发者大量采用网页技术，微软自身也开始放弃 WinUI，转而使用由 Microsoft Edge，也就是 Chromium 的一个分支，提供支持的 WebView2。

不过，目前还无法确认 WinUI 的重新推进是否能够说服微软内部不同产品团队投入这一原生框架。因此，即使新版 Outlook 和 Teams 在未来数月甚至数年内仍然采用网页技术，也不必感到意外。

单纯用 WinUI 替代网页应用还不够，因为 WinUI 自身也存在性能问题，而这些问题必须首先得到解决。微软对此十分清楚。

在 Build 2026 大会上，长期参与 Windows 桌面图形界面技术开发的克里斯·安德森表示，微软当前最重要的任务是关注“性能、基础功能、质量以及修复大量漏洞”。他还透露，微软已经“投入大量资源来显著改善内存使用情况”。

近期的一项改进，是将 WinUI 进程迁移到系统合成器中。微软认为，这一变化“应该能够带来更进一步的性能提升”。

微软尚未说明这些改进全面推出后，WinUI 的具体表现会达到什么程度，因此目前还没有明确数据。比如，一款占用 300MB 内存的 WinUI 应用是否会降至 200MB，暂时无法确认，但用户可以期待更加合理的资源管理。

安德森在 Build 2026 开发者大会上表示：“我想谈谈我们需要推进的工作，只有完成这些工作，我们才有资格去构建其中一些产品。这些其实就是人们一直在要求、也是在 WinUI 之上实现高效工作的核心能力。首要任务是性能、基础功能、质量以及修复大量漏洞。”

如今，WinUI 的开发已经转移到 GitHub，开发者可以直接跟踪微软正在进行的性能修复、回归问题处理以及其他代码变更。

不过，虽然 WinUI 开发已经公开进行，独立开发者和微软合作伙伴目前还不能直接参与贡献。

现阶段，拉取请求仍然全部来自微软内部开发者。微软表示，当前正在端到端验证“贡献流程、验证机制、文档以及发布流程”。

微软解释称：“我们正在利用这一阶段，端到端验证贡献流程、验证机制、文档以及发布流程。目标很简单：当社区拉取请求开放后，贡献者应该能够使用可靠且可预测的流程。我们希望先把这些工作做好，而不是仓促开放，团队正在朝这一目标努力。”

微软表示，等相关流程准备就绪后，社区拉取请求将会开放。这意味着，独立开发者可能还需要等待数周，才能参与改进 WinUI，甚至帮助完善 Windows 外壳。

此前，笔者曾报道 WinUI 再次成为微软重点后，一些用户开玩笑称，微软最终可能会重新开发一个框架和一套设计语言，从而再次制造混乱的界面一致性问题。

但微软已经在 Build 2026 大会上直接回应并否认了这种可能性。

微软表示：“我要明确说明，不，我们无意开发新的框架。事实上，我们正在放弃版本号，今后只称其为 WinUI，因为我们无意对它进行大规模调整，也不打算引入破坏性变更。”

微软还表示，WinUI 正在以更快速度融入 Windows 外壳。

微软称：“我们正在努力拓展 WinUI，使其能够适用于我们希望覆盖的任何场景。我们已经开始以更快速度将它集成到系统外壳中。因此，大家将会看到，微软推出的许多第一方功能都会基于 WinUI 构建。”

将 WinUI 的开发过程公开，是微软朝这一方向迈出的第一步。这不仅能让外界更透明地了解 WinUI 即将获得的功能和性能改进，也能让更广泛的开发者社区与微软建立更紧密的联系。
